# ETC 压缩单步：一张 100×100 怎么变成 5000 字节

> 上一篇：[板块总览](./) ｜ 下一篇：[ASTC 压缩单步 + 100×100 实例](./astc-encode-100x100)
> 数据可信度：全部来自配套 Python 教学编码器（穷举 flip×2、mode×2、table×8×8 选最小 MSE）对 100×100 测试图的真实输出；生成 bitstream 已用 **Mesa 口径解码器逐像素对拍 625 块 = 10000 像素零差异**。

## 编码全流程（先看宏观七步）

```
100×100 原图
  ① 切成 4×4 块          → 25×25 = 625 块
  ② 对每个块：分成两个子块  → flip 决定：左右两半 or 上下两半
  ③ 各子块求平均色          → 得到"基色"候选
  ④ 选模式：differential or individual（子块2 = 子块1 ± 小量？）
  ⑤ 搜索强度修正表          → 8 张表 × 2 张/块，共 8×8=64 种组合
  ⑥ 每个像素从 4 档修正里挑最近的
  ⑦ 打包成 64 bit（8 字节）
  → 全图 625 × 8 = 5000 字节
```

核心思想一句话：**每个 4×4 块只存「2 个基色 + 2 张修正表 + 每像素 2bit 索引」，共 64bit（4bpp）**。

## ① 分块

100 是 4 的倍数 → 25×25 = **625 块**，每块独立处理（块之间没有任何依赖，这也是并行压缩/并行解码的前提）。

![100x100 切成 4x4 块](./assets/grid-4x4.png)

> 💡 **看图要点**：白色网格把图切成 625 个 4×4 块。每个块从这一刻起**完全独立**——这也是为什么块压缩天然可并行、GPU 采样能按块随机寻址（`addr = (y/4) * 每行块数 + (x/4)`）。

## ②~③ block(0,0) 实例：分半 + 求均值

取左上角 block(0,0)，它落在 Q1 渐变最亮处。下面这张图把它的 16 个像素放大、标出每个像素的 RGB 值，并用红/蓝半透明底标出"左右切分"后两个子块的分工：

![block(0,0) 原始 16 像素与子块划分](./assets/annot/etc-q1-block-before.png)

原始 16 像素（行主序，同上图数值）：

| y\x | x=0 | x=1 | x=2 | x=3 |
|---|---|---|---|---|
| y=0 | (255,0,0) | (252,0,2) | (249,0,5) | (247,0,7) |
| y=1 | (252,0,2) | (249,0,5) | (247,0,7) | (244,0,10) |
| y=2 | (249,0,5) | (247,0,7) | (244,0,10) | (241,0,13) |
| y=3 | (247,0,7) | (244,0,10) | (241,0,13) | (239,0,15) |

肉眼可见：红色从 255 缓降到 239，蓝色从 0 缓升到 15——平滑渐变。编码器先试两种切法：

- flip=0：**左右两半** → 子块1 = x∈{0,1} 两列，平均 `(249,0,5)`；子块2 = x∈{2,3} 两列，平均 `(244,0,10)`
- flip=1：**上下两半** → 平均色几乎一样（渐变两个方向都缓）

> 🎯 **0 基础解读**：平均色就是"这一半 8 个像素的中间色"。ETC 的赌注是：块内像素都离这个中间色不远，后面只需记录每个像素"比中间色亮一点还是暗一点"。

## ④ 选模式：differential vs individual

两个子块平均色相差很小（红差 5、蓝差 5，且都在 0..31 的 5bit 范围内）→ 用 **differential 模式**：只存子块1 的 RGB555 + 每通道 3bit 差分（−4..+3），子块2 由"基色+差分"推出。

- 子块1 基色量化：`avg(249,0,5) → codeword (31,0,1)`，扩展回 8bit = `(255,0,8)`
- 差分搜索：让子块2 的扩展色最接近 `(244,0,10)` → `dR=-1, dG=0, dB=0`
- 子块2 实际还原 = `(255+(-1→247? ) ... )` —— 精确算：codeword `(31-1, 0, 1) = (30,0,1)`，扩展 = `(247,0,8)`

**为什么能省**：individual 每个子块存独立 RGB444（每通道 4bit），两个子块 24bit；differential 用 RGB555 + 3×3bit 差分，两个子块只要 `15+9=24bit`——同样 24bit，differential 的主基色多了 1bit 精度。自然图里 4×4 邻域颜色接近，差分几乎总赢。本图 625 块里 **differential 390 块（62%）**。

**什么时候 individual 赢**：两个子块颜色差异超过差分 ±4 范围（约 ±32/255）——跨材质边界、高频块。本图 **235 块（38%）**选了 individual。

## ⑤ 搜索强度修正表

即使基色差 1，也不能让所有像素都等于基色（会糊）。每子块再选一张 8 行的**强度修正表**，每行 4 档修正值：

| table | 档0(+a) | 档1(+b) | 档2(−a) | 档3(−b) |
|---|---|---|---|---|
| 0 | +2 | +8 | −2 | −8 |
| 1 | +5 | +17 | −5 | −17 |
| 2 | +9 | +29 | −9 | −29 |
| … | | | | |
| 7 | +47 | +183 | −47 | −183 |

block(0,0) 两块基色 (255,0,8)/(247,0,8) 都已接近目标，只需要**微调**→ 编码器给子块1 选 table1=1（±5/±17），子块2 选 table2=0（±2/±8）。表格搜索是编码器最重的部分：`8 表 × 8 表 × 16 像素 × 4 档`，全图 625 块 × 64 组合 ≈ 40 万次候选评估——这就是"块压缩慢在编码器"的原因之一。

## ⑥ 每个像素挑一档

对每个像素，在 4 档修正色里挑最近基色+修正值的组合。block(0,0) 的 16 个像素**全部选了档 2**（−a 小负）：

- 左半（子块1）：`(255,0,8) + (−5) = (250,0,3)`
- 右半（子块2）：`(247,0,8) + (−2) = (245,0,6)`

解码还原后，16 个像素只有这两种颜色——**块内实际只剩 2 色**。这不是 bug，是 ETC1 的设计边界：基色 + 标量修正只能表达"沿灰度轴的一小段"，Q1 渐变每块内红蓝同时缓变，颜色其实在 RGB 空间沿对角线走，ETC1 只好把它压成最接近的两点。整块最终 MSE = 10.35（48 个分量平均）。

## ⑦ 打包：64bit 怎么排

最终选择：`diff=1, flip=0, table1=1, table2=0, base1=(31,0,1), dR=−1`。64bit 小端读取写作十六进制：

```
ff000822ffff0000
```

下面把 64bit 画成色带——每一段一个颜色对应一个字段，字段名标在下方，刻度是真实 bit 位号：

![ETC1 64bit 字段分布色带](./assets/annot/etc-64bit-fields.png)

逐字段拆开（bit 63 → bit 0，MSB 在左）：

| 字段 | bit 范围 | 值 | 含义 |
|---|---|---|---|
| R (RGB555) | 63..59 | 31 → 255 | 子块1 红 |
| dR | 58..56 | 7（两补=−1） | 子块2 红偏移 |
| G | 55..51 | 0 | 子块1 绿 |
| dG | 50..48 | 0 | |
| B | 47..43 | 1 → 8 | 子块1 蓝 |
| dB | 42..40 | 0 | |
| table1 | 39..37 | 1 | 子块1 修正表 |
| table2 | 36..34 | 0 | 子块2 修正表 |
| diff bit | 33 | 1 | differential 模式 |
| flip bit | 32 | 0 | 左右切分 |
| 像素索引 MSB 平面 | 31..16 | 每像素 1bit | 见下 |
| 像素索引 LSB 平面 | 15..0 | 每像素 1bit | 见下 |

像素索引的 2bit 被拆成**两个 16bit 平面**（MSB 平面 + LSB 平面），像素 (x,y) 的位位置 = `y + 4x`（列主序）。两个平面分离是为了硬件能**一次 16bit 读取拿到一行 16 个像素的同一 bit**。本块 16 个索引全是 `10b`（=2）→ LSB 平面全 0、MSB 平面全 1，体现在 hex 上就是低 32bit 的 `0000`（LSB）+ `ffff`（MSB）。

> 对照直觉：64bit = `R(5)+dR(3) + G(5)+dG(3) + B(5)+dB(3) + 表1(3) + 表2(3) + diff(1) + flip(1) + 像素(32)` = 63…差 1？不——数一遍：15+3×3=24、+3+3=6、+1+1=2、+32 = **64**，正好。

## 解码还原：看看刚才压成了什么

![block(0,0) 压缩前后对比](./assets/annot/etc-block-before-after.png)

左边是原始 16 像素（每个像素 RGB 都不同），右边是"这 8 字节解码回来"的 16 像素——**只剩 2 种颜色**：左半全 `(250,0,3)`、右半全 `(245,0,6)`。每个格子的 Δ 行标出了误差（还原 − 原始），红色系文字表示这一格确实丢了信息。

这就是有损压缩的真实样子：不是"模糊一点"，而是**把每 8 个像素强行合并成同一种颜色 + 一个小修正**。0 基础读者看到这张图，就理解了为什么 ETC1 对色相渐变（Q1 那种红→蓝同时变化）无能为力——它只能沿"亮度"一个方向修正。

## 全图结果

| 项 | 值 |
|---|---|
| 总块数 | 625（25×25） |
| 文件大小 | 625 × 8 = **5,000 B**（原图 RGBA8 30,000 B = 6:1；RGB8 10,000 B = 2:1） |
| 模式分布 | differential 390 / individual 235 |
| table 组合 | (0,0) 319 块、(1,0) 241 块——平坦区占绝大多数 |
| 解码 PSNR | **29.71 dB** |

![原图 vs ETC1 解码放大 2x](./assets/test-100x100.png)  ![ETC1 解码](./assets/dec-etc1.png)

按象限看误差，模型假设（色相恒定、只有明暗变化）被验证得清清楚楚：

| 象限 | 内容 | 平均 MSE | 直觉 |
|---|---|---|---|
| Q3 | 灰渐变（纯亮度变化） | **17.07** | 完全符合"沿灰轴"假设 → 最好 |
| Q1 | 红→蓝对角渐变（色相变化） | 27.57 | 块内两色压成两点 → 糊 |
| Q2 | 同色相硬边 | 32.81 | 差分能近似，边界块仍损失 |
| Q4 | 棋盘 + 亮点（高频） | **215.15** | 高频 = 块压缩杀手（各块 max 可达 2821） |

## 源码解析：这些单步在代码里长什么样

上面每步都能在本板块配套 Python 教学编码器（`etc1_enc.py`，625 块已与 Mesa 口径解码器逐像素对拍零差异）里找到一一对应的代码。编码器核心 `encode_block2` 的骨架（行号对应真实文件）：

```python
# etc1_enc.py:32  encode_block2(px)：编码一个 4×4 块，返回 64bit 字
for flip in (0, 1):                      # ① 两种切分都试
    ...
    base555 = [clamp(round(avg[0][c] / 8.0), 0, 31) ...]   # L46 ③ 子块1 均值→RGB555
    for d in range(-4, 4):               # L50 ④ 差分 −4..+3 逐通道搜索
        ...                              #      让 子块2扩展色 最接近子块2均值
    for mode in ('diff', 'ind'):         # ④ 两种模式都试
        for tb1 in range(8):             # L64 ⑤ 8×8 张修正表穷举
            for tb2 in range(8):
                ... 每个像素从 4 档里挑最近的（⑥），累计 MSE
if best is None or mse < best[0]: ...    # 留下 MSE 最小的组合
# ⑦ 按 KDF 位布局打包：R1<<59 | dR<<56 | G1<<51 ... | diff<<33 | flip<<32
```

观察点：**真正的算法重活全在编码器**（46 行的 `for d in range(-4,4)` 起，三层循环 = 2×2×64 组合/块）；解码器 `decode_block`（L105）只是一次字段移位 + 查表 + 加法。这也是移动端 GPU 的常态：**解码是硬件免费送的，压缩是离线的贵活**。

## ETC2 救得了哪些块？

ETC2（向后兼容扩展，vault 有完整机制）新增 T/H/Planar 三模式，其中 **Planar 用 3 个角点色做双线性插值**，专治渐变——实测对纯渐变块 ETC2 Planar 的 MSE 可以从 645 掉到 1.3（约 +27 dB）。Q1 那种对角双通道渐变正是 Planar 的甜区。

本板块 ASTC 文章里 4×4 footprint 对同一张图 PSNR 55 dB，差距主要来自：**ASTC 的 weight 每像素独立 + 端点色任意方向插值**，不受"灰度轴"限制。
