# ETC / ASTC 纹理压缩：编码器单步详解

> 上一篇：无（板块首页）｜ 下一篇：[ETC 压缩单步 + 100×100 实例](./etc-encode-100x100)
> 数据可信度：本板块所有数字来自**真实编码器输出**——ASTC 用 ARM 官方 astcenc v5.7.0（`-cl -fast`）压 100×100 测试图后逐块解析 128bit 位流（解析器按官方 `physical_to_symbolic` 移植）；ETC1 用配套 Python 教学编码器生成合法 bitstream，并用 **Mesa 口径解码器逐像素对拍 625 块零差异**。

## 一句话模型

> **GPU 纹理压缩 = 把每块像素"切块 → 找两个端点色 → 让每个像素在端点之间挑一个插值权重"。**
> 与 PNG/JPEG 不同，它是**定长块 + 随机寻址**：任何一块的位置都能用 `addr = (y/4) * blocksPerRow + (x/4)` 直接算出，GPU 采样单元才能硬件实时解压。

本站已有完整**格式原理**笔记（vault：《ETC 与 ASTC 纹理压缩实现原理》，43KB，含比特布局/规范表格/交叉验证方法论）。本板块补的是另一面——**编码器视角的单步操作**：一张图进来之后，每个块到底怎么一步步变成 64/128 个 bit。

## 贯穿全程的教学图：一张 100×100

所有单步例子都用同一张程序生成的 100×100 测试图。四象限各考一种编码场景：

| 象限 | 内容 | 在考什么 |
|---|---|---|
| Q1 左上 | 红→蓝对角渐变 `t=(x+y)/98` | 平滑双通道渐变（块压缩最难点之一） |
| Q2 右上 | 亮黄 `(200,180,60)` / 暗黄 `(40,36,12)`，硬边在 x=75 | 两个色簇 + 一条硬边 |
| Q3 左下 | 灰 30→230 上下渐变 | 单通道明暗渐变 |
| Q4 右下 | 16px 蓝/橙棋盘 + 稀疏白点 `(x+y)%37==0` | 高频纹理 + 孤立亮点 |

![100x100 测试图](./assets/test-100x100.png)

选 100 有讲究：它是 4、5 的倍数，**正好整除 ETC1/4×4/5×5**；对 6×6 又**不整除**（100/6=16.67）——一个 footprint 恰好能讲"非倍数尺寸要 pad"这个真实工程坑（P0 级，vault 有记录）。

## 三组真实数据预览

| 格式 | 切成几块 | payload | bpp | 解码 PSNR |
|---|---:|---:|---:|---:|
| ETC1（4×4 → 64bit） | 25×25 = 625 | 5,000 B | 4.00 | 29.71 dB |
| ASTC 4×4 | 25×25 = 625 | 10,000 B | 8.00 | **55.02 dB** |
| ASTC 5×5 | 20×20 = 400 | 6,400 B | 5.12 | 51.67 dB |
| ASTC 6×6 | 17×17 = 289 | 4,624 B | 3.56 | 42.67 dB |
| （对照）RGBA8 原图 | — | 30,000 B | 32 | ∞ |

同样一块区域，ETC1 只有 29.7 dB 而 ASTC 4×4 有 55 dB——差异全在这两篇文章的单步里。
