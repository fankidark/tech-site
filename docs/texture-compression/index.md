# 纹理压缩总览：128 位里到底塞了什么

## 一句话结论

> **GPU 纹理压缩的火柴盒只有两个尺寸：64 bit 和 128 bit。**
> 所有格式的差别，都是"这 128 位里，多少位给端点色、多少位给每个像素的权重、多少位给'怎么解释这块'的配置"。
> 编码器的全部工作，就是在这个固定预算里做取舍。

这一句话能解释本板块后面几乎所有现象：ETC1 为什么怕色相渐变、ASTC 6×6 为什么体积省一半画质掉 12 dB、BC1 为什么在白赚 1-bit alpha 时要牺牲画质。

## 它到底解决什么问题

GPU 每帧要从一张贴图上采样几百万次。如果贴图是未压缩的 RGBA8，一张 1024×1024 就要 4 MB 显存，采样时还要在 4 MB 里随机跳 —— 显存带宽立刻见底。

那用 PNG/JPEG 行不行？

| | PNG/JPEG | 块压缩（ETC/ASTC/BC） |
|---|---|---|
| 解压方式 | 变长编码 + 熵解码，要顺序读 | **定长块 + 随机寻址** |
| 找某个像素 | 得从头解到那里 | `addr = (y/4) * blocksPerRow + (x/4)` 直接算 |
| 谁来解 | CPU 软件解码 | **GPU 采样单元硬件实时解压** |
| 能当纹理直接采样吗 | 不能，必须先解成 RGBA8 | 能，采样器边采边解 |

关键就是"定长块"这一条。因为每块大小固定，任意一块的地址能四则运算直接算出来，**显存里不需要任何索引表**，GPU 才能把它做成硬件电路。代价是压缩率被锁死：一张图和它的体积关系是线性的，没有 JPEG 那种"内容简单就压得小"的弹性。

生活类比：JPEG 像把一本书重新排版、删掉冗余词句（读的时候得从头顺下来）；块压缩像把书切成一张张固定大小的卡片，每张卡片写满 64 个格子 —— 你随时能抽第 137 张卡片看第 9 个格子，但每张卡片只有 64 格，写不下就是写不下。

> 这里必须说清：块压缩的"压缩"不是"信息变少所以文件变小"，而是**先规定体积上限，再把画质做到该上限下的最好**。这是有损压缩里"率失真优化"的思路，不是无损压缩的思路。

## 术语先对齐

| 术语 | 一句话解释 |
|---|---|
| **块 / block** | 压缩的最小单位。本板块的格式都是 4×4 = 16 像素一块（ASTC 可以更大） |
| **footprint** | ASTC 术语：一块覆盖多少像素，4×4 到 12×12 都能选 |
| **bpp**（bits per pixel） | 平均每个像素分到多少 bit。8 bpp = 每像素 1 字节 |
| **端点色 / endpoint** | 一个颜色，块内像素在若干端点之间"插值"选色 |
| **权重 / weight** | 像素在端点之间插值的比例，0 = 靠近端点 A，最大档 = 靠近端点 B |
| **分区 / partition** | 一块内部再切成的若干区域，各自有独立的端点色 |
| **CEM** | Color Endpoint Mode：端点数据怎么存（8bit？base+offset？HDR？） |
| **void-extent 块** | ASTC 的特例：整块恒定颜色，只存 RGBA 各 16bit 常量，不做插值 |
| **PSNR** | 画质指标，单位 dB，越高越好。对 8bit 图，40 dB 以上肉眼很难看出差别 |
| **pad** | 图尺寸不是 footprint 倍数时，补到倍数再压（会产生无效像素） |

## 贯穿全程的教学图：一张 100×100

本板块所有单步例子都用同一张程序生成的 100×100 测试图。四象限各考一种编码场景：

| 象限 | 内容 | 在考什么 |
|---|---|---|
| Q1 左上 | 红→蓝对角渐变，`t=(x+y)/98`，`r=255(1−t)`、`b=255t` | 平滑**双通道**渐变（块压缩最难点之一） |
| Q2 右上 | 亮黄 `(200,180,60)` / 暗黄 `(40,36,12)`，硬边在 x=75 | 两个色簇 + 一条硬边 |
| Q3 左下 | 灰 30→230 上下渐变 | 单通道明暗渐变 |
| Q4 右下 | 16px 蓝/橙棋盘 + 稀疏白点 `(x+y)%37==0` | 高频纹理 + 孤立亮点 |

![100x100 测试图](./assets/test-100x100.png)

> ⚠️ **一个容易踩的坑**：仓库里这张 `assets/test-100x100.png` 实际存储是 **200×200**（2×2 像素一组的抗锯齿放大版），文章的"100×100"是它的**逻辑尺寸**。用站点教学编码器实测：把它 2×2 盒式下采样到 100×100 再压 ETC1，得到 **29.71 dB**，与文章里的数字逐个吻合；直接压 200×200 那张会得到 37.97 dB（块数 2500），两者不是一回事。看图看内容，算数据要按逻辑尺寸。

选 100 有讲究：它是 4、5 的倍数，**正好整除 ETC1/4×4/5×5**；对 6×6 又**不整除**（100/6=16.67）—— 一个 footprint 恰好能讲"非倍数尺寸要 pad"这个真实工程坑。

## 三组真实数据预览

| 格式 | 切成几块 | payload | bpp | 解码 PSNR |
|---|---:|---:|---:|---:|
| ETC1（4×4 → 64bit） | 25×25 = 625 | 5,000 B | 4.00 | 29.71 dB |
| ASTC 4×4 | 25×25 = 625 | 10,000 B | 8.00 | **55.02 dB** |
| ASTC 5×5 | 20×20 = 400 | 6,400 B | 5.12 | 51.67 dB |
| ASTC 6×6 | 17×17 = 289 | 4,624 B | 3.56 | 42.67 dB |
| （对照）RGBA8 原图 | — | 30,000 B | 32 | ∞ |

同样一块区域，ETC1 只有 29.7 dB 而 ASTC 4×4 有 55 dB —— 差异全在这几篇文章的单步里。注意这张表里 **ASTC 那三行拿的是 8 bpp 换画质、再往上几乎是白送的**：4×4 到 5×5 体积降 36% 只掉 3.4 dB，但 5×5 到 6×6 再降 28% 就掉 8.9 dB。**收益递减的拐点在 5×5 和 6×6 之间**，这是本板块最实用的一条工程结论。

## 常见误解 / 踩坑

::: warning 三个最常见的想当然
1. **"压缩率可以更高"** —— 块压缩的体积是同尺寸线性确定的。625 块就是 5000 B，跟图里画了什么毫无关系。想要更小只有一个办法：换更大的 footprint（代价是画质）。
2. **"PSNR 高就等于好看"** —— PSNR 是全图平均误差，对局部惨案不敏感。Q4 那种高频棋盘区域 MSE 能到 215，全图 PSNR 却还有 29.7 dB。**看 PSNR 一定要配合误差热图看**，实验台的第三张画布就是干这个的。
3. **"`-cl` 就是 LDR，位流里不该出现 HDR 端点"** —— 实测反例见 [ASTC 篇](./astc-encode-100x100)：`-cl` 压出的位流里真的有 HDR CEM。规范允许的组合比直觉多。
:::
