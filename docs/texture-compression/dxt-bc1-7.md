## 一句话结论

> **BC 家族 = 线性调色板：每块存 2 个 16bit 端点色，让像素在两个端点之间"拉一条线段"上选点。**
> 各成员的区别只在"额外那 64 bit 拿来存什么"：BC1 全给颜色、BC2/BC3 给 alpha、BC4/BC5 给单/双通道数据、BC6H/BC7 用更复杂的模式把 128 bit 花得更聪明。

## 它到底解决什么问题

ETC 的思路是"基色 + 沿灰度轴修正"——只有一个自由度（更亮还是更暗）。这在 PC/主机平台上不够用：那里的贴图色相变化远比手机游戏复杂（UI 图标、彩色角色、光照贴图）。

BC1（也就是 DXT1）换了个更直接的办法：**直接在这 16 个像素的颜色里拉一条直线**，每个像素挪到直线上离自己最近的位置。

生活类比：ETC1 是给你一支**只有明暗可调的笔**，让你在纸上把 16 个点画得接近原图；BC1 是允许你把**整张纸旋转到任意角度**再画那条线。多出来的这一个自由度，就是 DXT 家族在 PC 上统治十几年的根本原因。

## 术语先对齐

| 术语 | 一句话解释 |
|---|---|
| **BC** | Block Compression，微软 DirectX 的块压缩家族统称，前身叫 DXT |
| **BC1 / DXT1** | 64 bit：2 个 RGB565 端点 + 16 个 2bit 索引 |
| **端点 c0 / c1** | 那条"线段"的两个端点，以 RGB565 打包成 16bit |
| **调色板** | 由 c0、c1 插值出的 4 个候选色 |
| **3-color 模式** | `c0 ≤ c1` 时第 4 档变成全透明黑，白赚 1-bit alpha |
| **RGB565** | 红 5 bit、绿 6 bit、蓝 5 bit 的打包色（绿色多 1 bit 因为人眼最敏感） |
| **BC4 / BC5** | 不用颜色，整块压单通道（BC4）或两个单通道（BC5） |

## BC1（DXT1）：最基础的线性调色板

### 机制单步（与 ETC1 对照学）

| 步骤 | BC1 | ETC1（对照） |
|---|---|---|
| 每块 | 4×4 → **64bit（8B）** | 4×4 → 64bit（8B） |
| 存什么 | 2 个 **RGB565** 端点 + 每像素 2bit 索引 | 2 个基色 + 2 张修正表 + 每像素 2bit 索引 |
| 像素还原 | 在 c0→c1 线段上插值：`c0, c1, ⅔c0+⅓c1, ⅓c0+⅔c1` | 基色 ± 修正表（同一亮度方向） |
| 端点方向 | **RGB 空间任意方向** | 只有"更亮/更暗"一个方向 |
| 配置位 | **0 bit**（模式靠 c0/c1 大小偷偷表达） | 6 bit（table1/table2/diff/flip） |

### 位域解剖：64 bit 怎么分

BC1 的位布局比 ETC1 简单得多——**没有任何配置位**：

  :width="64"
  title="BC1 的 64bit：一半给端点、一半给索引，配置位为 0" />

数一遍：`16(c0) + 16(c1) + 32(索引) = 64`。**索引占了整整一半**——这与 ETC1 完全一样（ETC1 也是 32 bit 索引）。区别在于 ETC1 那另外 32 bit 里塞了 2 张修正表 + 模式 + 方向，而 BC1 把它们全省下来给了端点色精度（16bit 端点 vs ETC1 的 5bit 基色）。

> **这就是两种范式的分野**：ETC1 用"低精度端点 + 查表修正"表达颜色；BC1 用"高精度端点 + 自由方向"表达颜色。同样 64 bit，谁赢取决于图的色相是否丰富 —— 见下面的真数据。

### 特殊技巧：3-color + 1bit 透明

BC1 存两个 16bit 数，比较它们的**数值大小**就能多表达一种模式：`c0 > c1` 时按 4-color 解码；`c0 ≤ c1` 时按 **3-color + 透明**解码（第 4 档 = 全透明黑）。

这就是"1-bit alpha"——**不花额外空间**（判据就是那 16 个 bit 自己），植被/铁丝网这类要么全透要么不透的贴图白赚一个 alpha。

> ⚠️ 这也解释了 DDS 里 `DXT1` 处理 alpha 的经典坑：如果原始图某些块需要 4-color 插值但又要透明，编码器被迫在"画质"和"透明"里二选一——这也是 BC1 不太适合 UI 的原因之一。

## BC2 / BC3：把 alpha 单独拿出来存

BC1 的 1bit alpha 不够半透明用。BC2/BC3 把块扩到 **128bit**：颜色部分沿用 BC1 的 64bit，另外 64bit 存 alpha：

| 格式 | 颜色部分 | alpha 部分 | 适合 |
|---|---|---|---|
| BC1/DXT1 | 64bit（2 端点） | 1bit（3-color 技巧） | 不透明贴图 |
| BC2/DXT3 | 64bit BC1 | **4bit × 16 像素**（显式，无插值） | 硬 alpha 边缘 |
| BC3/DXT5 | 64bit BC1 | **2 端点 + 3bit × 16 像素**（8 档插值） | 平滑半透明 |

BC3 的 alpha 通道就是"**单通道版 BC1**"（α0、α1 两个 8bit 值，中间插 6 档）——这个思路再进一步就是 BC4。

## BC4 / BC5：压根不用颜色

有些数据不是颜色：单通道高度图、双通道法线（XY）。BC4 把整块 64bit 全用来压单通道（2 端点 8bit + 每像素 3bit，8 档）；BC5 是两个 BC4（128bit）——**法线贴图用 BC5 存 XY 是 PC 多年的标准姿势**（Z 由单位长度重建，不用存）。

为什么法线不能直接用 BC3？因为 BC3 的颜色部分仍是 RGB 端点插值——法线的 X、Y 是**独立的两个通道**，捆在一条线段上插值会互相干扰。BC5 给每个通道独立的端点和插值，这才是对的。

## BC6H / BC7：128bit 高端局

| 格式 | 面向 | 机制一句话 | 备注 |
|---|---|---|---|
| BC6H | **HDR** RGB | 半浮点端点（有符号/无符号）压缩 | 不能压 alpha；lightmap/IBL 用 |
| BC7 | 最高质量 LDR RGBA | **8 种模式**：1~3 个分区、4~8 个端点、不同权重精度，编码器逐块挑 | 无 1bit alpha 技巧，真正 8bpp 高质量 |

BC7 的 8 种模式很像 ASTC 的"配置化"雏形（但没有 ASTC 的 footprint 可变和 trit/quint）。BC7 编码器要试 64 种分区 × 多种端点组合——和 ASTC 一样**慢而精**。

## 与 ETC/ASTC 的范式差异（一张表）

| 维度 | BC1/BC3/BC5 | ETC1/ETC2 | ASTC | BC7 |
|---|---|---|---|---|
| 块大小 | 4×4 固定 | 4×4 固定 | 4×4~12×12 | 4×4 固定 |
| 每块 bit | 64/128 | 64/128 | 恒定 128 | 128 |
| 表达范式 | 线性调色板 | 基色+亮度修正 | 端点+weight（可配置） | 端点+weight（8 模式） |
| 配置位开销 | **0 bit** | 6 bit | **17 bit** | 模式号内嵌 |
| 分区 | 无 | 无（ETC2 有 T/H 但规则） | 1~4 不规则（10bit seed） | 最多 3 个规则分区 |
| alpha | 1bit（BC1）/显式/插值 | EAC/1bit | CEM 任意组合 | 每模式内嵌 |
| HDR | 仅 BC6H | 不支持 | 支持（HDR CEM） | 不支持 |
| 平台 | PC/主机（DX） | Android/移动（GLES） | 移动+桌面新硬件（ES 3.2+/Vulkan） | PC/主机（DX11+） |
| 硬件解压 | 有 | 有 | 有 | 有 |

注意"配置位开销"这一行：**BC1 是 0、ETC1 是 6、ASTC 是 17**。这三位数字正好对应三种范式的灵活性——也对应它们的编码器耗时。

## 0 基础一分钟版

把 16 个像素想成 RGB 空间里的 16 个点：

- **BC1**：在这堆点里拉一条直线（两个端点），每个点挪到直线上离自己最近的位置 → 8 字节
- **ETC1**：不找直线，而是"把整堆点拍扁到亮度轴" → 也是 8 字节，但方向被限制
- **BC7 / ASTC**：如果 16 个点聚成两三堆（不同材质交界），就先分区再各自拉线 → 16 字节

## 常见误解 / 踩坑

::: warning 五个 BC 家族常见坑
1. **"BC1 也是 4×4 一块，那和 ETC1 差不多"** —— 块的形状一样，但**表达模型完全不同**（线段 vs 灰度轴，见对照表）。同图 0.7 dB 的差距只是这张测试图的巧合。
2. **"`c0 > c1` 是格式要求所以编码器必须升序排"** —— 不是升序，恰恰相反：**必须保证 c0 数值大于 c1** 才走 4-color 分支。如果原始两个端点的量化值反了，要主动交换（`textureEncoders.js:122`）。忘了交换，整块就走 3-color+透明，画质和透明度一起崩。
3. **"BC1 的 alpha 是压缩出来的"** —— 它根本没存 alpha，是把"第 4 档调色板"挪用成全透明黑。所以透明像素的颜色信息完全丢失。
4. **"法线贴图用 BC3 就行"** —— BC3 的 RGB 部分仍是端点插值，XY 会互相干扰。法线要用 **BC5**（两个独立通道）。
5. **"BC 都是 PC 的，跟移动端无关"** —— BC7 在 Vulkan / D3D11 级别硬件上也能用；跨平台项目更常见的做法是用 Basis Universal/KTX2 做中间格式，运行时转码到各平台原生格式。
:::
