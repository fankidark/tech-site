# 🧪 纹理压缩实验台

> 上传一张图，**亲眼看它被块压缩的每一步**：切块 → 逐块编码（基色/端点/权重怎么算、怎么打包成 64/128bit）→ 解码对比 → 误差热图。点解码图上的任意块可下钻该块完整单步数据。

## 怎么用

1. **图片**：内置四象限测试图（覆盖渐变/色相/暗色块/高频棋盘四种编码场景），或上传你自己的图（会自动缩放到所选尺寸）
2. **尺寸**：100×100 标准（4×4 与 5×5 整除、6×6 触发 pad——正好演示非倍数尺寸的工程处理）；120×120 三种 footprint 全部整块；160×160 更大更慢
3. **格式**：
   - **ETC1 / BC1**：真实编码器（穷举求最优 64bit），输出真实合法 bitstream
   - **ASTC 4×4/5×5/6×6**：教学编码器——输出**真实合法 bitstream**（ARM 官方 astcenc 可直接解码；2026-09-10 端到端复测：100×100 下 4×4=**30.00dB** / 5×5=**35.50dB** / 6×6=**23.30dB**，6×6 的 100×100 含 pad；换成 120×120 无 pad 时 6×6 升到 **34.18dB**），但只做 bbox 端点 + 权重投影，不做分区/模式搜索，所以质量低于 astcenc 的 42~55dB
4. **压缩后**：三画布对照（原图 / 压缩解码逐块动画 / 误差热图），底部流水线日志列出每块真实决策；**点击②画布任意位置**弹出该块 ①原始像素 → ②解码含 Δ ③决策字段 → ④索引/权重网格 → ⑤完整 hex bitstream

## 一个必须讲清的坑：实验台的图和文章那张不是同一张

这是 0 基础读者最容易困惑的地方，先说破：

| | 文章里的 100×100 测试图 | 实验台内置的"四象限测试图" |
|---|---|---|
| 来源 | 仓库静态资产 `assets/test-100x100.png` | 实验台**运行时程序生成**（`TextureCompressionLab.vue:111` 的 `makeSample()`） |
| Q1 左上 | 红→蓝**双通道**对角渐变 | 灰阶渐变（`r=g=b`，见组件 `:116-117`） |
| Q4 右下 | 蓝/橙棋盘 + 稀疏白点 | 深蓝/亮黄棋盘（`pal` 与格子色见 `:120-126`） |
| ETC1 结果 | **29.71 dB** | **29.87 dB** |

两张图**长得像但内容不同**，所以数字不能互相引用。这不是 bug，是历史原因：文章的数据来自真实的 `test-100x100.png`，而实验台为了让页面**不依赖任何外部图片就能打开即用**，内置了一份"神似"的生成图。

## 端到端验收记录（2026-09-10，线上真实浏览器 Playwright）

| 用例 | 耗时 | 块数 | 输出 | PSNR | 日志 | 点块下钻 |
|---|---|---|---|---|---|---|
| ETC1 100×100 | 2.7s | 625（25×25） | 5000 B / 4.00 bpp | **29.87 dB** | 625/625 | ✅ block(12,11) → `1816120000FF00EC` |
| BC1 100×100 | 2.5s | 625 | 5000 B / 4.00 bpp | 34.32 dB | 625/625 | ✅ `0505050508618305` |
| ASTC 4×4 100×100 | 1.2s | 625 | 10000 B / 8.00 bpp | 30.00 dB | 625/625 | ✅ 16 B bitstream |
| ASTC 5×5 100×100 | 1.6s | 400（20×20） | 6400 B / 5.12 bpp | 35.50 dB | 400/400 | ✅ |
| ASTC 6×6 100×100（含 pad） | 2.4s | 289（17×17） | 4624 B / 3.70 bpp | 23.30 dB | 289/289 | ✅ block(8,7) |
| ASTC 6×6 120×120（无 pad） | 2.4s | 400（20×20） | 6400 B / 3.56 bpp | **34.18 dB** | 400/400 | ✅ block(10,9) |
| ETC1 160×160 | 2.6s | 1600（40×40） | 12800 B / 4.00 bpp | 41.24 dB | 1600/1600 | ✅ block(18,17) |

**0 个 console 错误。** 上面这些 PSNR 全部是用同一份 `encodeImage()` 在内置样例图上重跑得到的，逐个吻合——所以这张验收表可以放心引用。

两个可直接用于教学的对比：

- **pad 的代价**：ASTC 6×6 同图 100×100（pad）23.30dB → 120×120（无 pad）34.18dB，**差 10.9 dB**——尺寸取 footprint 倍数不是玄学
- **5×5 是教学编码器的甜点**：100×100 下 5×5（35.50dB）领先 4×4（30.00）与 6×6（23.30）；放大到 120×120 后 5×5 仍领先（43.65 vs 4×4 35.20 / 6×6 34.18）

> ⚠️ **别把这些数字和 ASTC 文章的 55.02 / 51.67 / 42.67 dB 混起来**：
> 那是**官方 astcenc 5.7.0** 在**文章测试图**上的成绩；这里是**教学编码器**在**实验台内置图**上的成绩。
> 编码器不同、图也不同 —— 教学编码器只做 bbox 端点 + 权重投影，不搜索分区与模式，所以系统性偏低。

## 常见误解 / 踩坑

::: warning 用实验台时的四个注意点
1. **"实验台的 PSNR 怎么和文章对不上"** —— 见上面那张表：图不同、编码器也不同。要横比必须在同一张图上用同一档编码器。
2. **"ASTC 教学编码器就是 astcenc"** —— 不是。它只保证**位流合法**（官方解码器能解），不保证质量。它的端点直接取块内 min/max，不做任何端点优化。
3. **"点块下钻的 hex 是预先写死的"** —— 不是，每次点击都是拿当前这次压缩的真实 `BigInt` 位流现渲染的。改了输入图，hex 就变。
4. **"160×160 只是更慢"** —— 它同时让三种 footprint 都不必 pad（160 能被 4/5/8 整除，但 6 仍有余数），所以 PSNR 普遍更高。尺寸和 footprint 的整除关系对结果影响很大。
:::
